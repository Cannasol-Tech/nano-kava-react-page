## Story Status System

| Status | Meaning |
|---|---|
| backlog | Not yet planned for sprint |
| ready-for-dev | Planned, requirements complete |
| in-progress | Actively being developed |
| blocked | Cannot proceed. A reason is required |
| review | Code complete, in review |
| done | Reviewed, tested, verified |

## Blocked Story Rules

- `Status: blocked`, `Blocked: true` and `Blocked-Reason: <explanation>`. All three are required.
- When unblocked, set `Blocked: false`, clear the reason and update the status.
- The stock `sprint_plan.py` does not recognise `blocked`, and `generate` overwrites it. Restore it by hand
  after running `generate`.

## Requirement Numbering (FR-<EE><NN>)

- `FR-<EE><NN>` is a two-digit Feature number followed by a two-digit sequence within that Feature. The
  Feature number is the epic number, so `FR-0203` is the third FR of Feature 2.
- Non-functional requirements use `NFR-<EE><NN>` on the same scheme.
- Feature codes are `F-0NN`. The Features table in `PRD.md` is the epic list, because there is no `epics.md`.

## Acceptance Test Tagging (MANDATORY)

- Every scenario carries `@FR_<EE><NN> @story_<epic>_<story>`, for example `@FR_0103 @story_1_1`. The tag
  uses **underscores**. Prose keeps the hyphen (`FR-0103`). A hyphenated tag matches no gate and silently
  claims no coverage.
- Every scenario carries exactly one tier tag, `@e2e` or `@service`. An `@e2e` scenario also carries
  exactly one surface tag, `@web`. An `@service` scenario carries no surface tag.
- Acceptance tests run end to end (Stephen, 2026-08-29). Use `@service` only for a requirement that
  nothing with a screen can observe.
- Never add an FR without at least one tagged scenario, and never add a scenario without its `@FR_` tag.

## Acceptance Suite Layout

- Features: `test/acceptance/features/epic-<N>-<slug>.feature` (one per epic) and
  `test/acceptance/features/user_flows.feature`
- Steps: `test/acceptance/steps/test_epic_<N>.py`. Steps shared by two or more epics go in
  `steps/common.py`. Fixtures and steps used by every epic go in `test/acceptance/conftest.py`.
- `make test-acceptance` runs the whole suite. `make test-acceptance FR=0101` runs one requirement.

## Test Levels

`docs/SOP/story-frontmatter.md` names its `ACs:` levels after a React Native stack. This repo's mapping
is row O2 of `docs/SOP/project-deviations.md` § Testing and traceability. It is proposed and awaits
Stephen's ruling. Under that mapping a story's `L3` AC is proved by an `@service` scenario, and its `L4`
AC by an `@e2e @web` scenario.

## Functionality Reports

Only a complete `make test-acceptance` run produces a functionality report. A run filtered with `FR=`
writes JUnit only, and that is deliberate. `check_acceptance_evidence.py` is a separate gate. It is
allowed to fail and never changes the suite's verdict. Reports are archived under
`_bmad-output/test-artifacts/functionality-reports/runs/`.
